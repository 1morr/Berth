# 86 — 簡化審計：找出「同一件事兩套做法」與「沒人用的東西」，列清單給使用者挑

**Status:** ready-for-agent

**Blocked by:** 83、84（搜尋那一塊正在重寫，先審會白審）

**讀:** `CLAUDE.md`（架構規則、依賴方向）；`docs/plan.md` §1（模組邊界）；`CONTEXT.md`（名詞表，判斷「同一個概念兩個名字」用）；`docs/progress.md`「偏差與決定」（哪些重複是刻意的、有理由的）；其餘按發現讀

## 為什麼（2026-10-10 使用者）

使用者希望整個程式是最簡實現、邏輯統一。這個 repo 做了八十幾張票，同一件事常在不同時期各加了一套做法。例如作品頁搜尋：

- 季的寫法有兩套：按搜尋加 `Season 3`，搜缺的集用 `S03`。這一項已由 84 處理。
- 過濾結果有三種處理：略過、收起來、結果表。這一項已由 83 處理。

這種重複不只搜尋一處。沒人整理的話會越積越多，讀的人也分不出哪一套才是對的。

## 做什麼

**這張只審、不改程式碼。** 產出一份清單，使用者挑中的項目才另外開票去改。

1. **只找兩類**：
   - **同一件事兩套做法**：同一個概念有兩份實作或兩個名字；同一個判斷寫在兩個地方，可能會各自長出不同的答案；同一種畫面元件做了兩個近似版本。
   - **沒人用的東西**：沒有呼叫端的函式、類別、匯出、API 端點、設定欄位、i18n key；只是在守著已經不存在的介面的測試；已經沒有消費者的相容分支。
2. **不找**：
   - 寫法風格、看順眼才想改的命名、為了將來可能用到而加的抽象。
   - 有理由的重複：progress.md「偏差與決定」或程式註解寫了理由的，列在清單的「刻意保留」區，不算發現。
3. **怎麼找**：
   - 依區塊分頭找：後端 `services`、`parser` / `naming` / `domain`、`adapters` / `api` / `pipeline`、前端 `web/src`。依全域規則，worker 用 sonnet。
   - 用工具掃一次沒人用的程式碼：Python 用 vulture，前端用 knip。工具的誤報要逐條排除，不能整份照抄。
   - 每一條發現都要再複核一次，確認真的是重複、真的沒人用。複核用 opus。沒通過複核的不列。
4. **清單**放在 `docs/research/simplification-audit-<日期>.md`，每一條寫：
   - 是什麼：兩套做法各在哪裡（`檔案:行`），或哪個東西沒人用。
   - 建議怎麼統一：保留哪一套、刪哪一套。
   - 改動大小：小（一個 session 內、一兩個檔）、中、大。
   - 風險：會不會動到對外介面、持久化資料、migration。
   - 依「值不值得改」排序。
5. **閘門建議**：工具掃出來的結果如果夠準，評估要不要把 vulture、knip 加進 pre-commit，讓「沒人用的程式碼」以後自動被擋下。要寫出誤報率、要加多少 whitelist；決定由使用者做。
